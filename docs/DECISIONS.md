## Архитектура (технические)

- **Переключатель демо-роли в меню профиля** (cookie + server action, работает только на демо-данных). Позволяет показывать продукт глазами менеджера, РОПа и директора. Это не авторизация.
- **Данные, зависящие от запроса, — внутри `<Suspense>`.** Требование Cache Components в Next 16 для мгновенной навигации: статичная часть страницы показывается сразу.
- **Фильтр по менеджерам — в адресе страницы (`?manager=`).** Ссылкой можно поделиться, кнопка «назад» работает.
- **Не подключённые к backend действия («Отложить», «Убрать из фокуса») показаны выключенными с пояснением**, а не спрятаны и не имитируют успех.
- ~~Модуль `features/dashboard` — агрегатор «Моего дня»~~ — удалён (28.10.2026).

- **Модули в `features/`, маршруты в `app/`, общие блоки в `components/shared`.** Границы модулей видны по структуре; страницы остаются тонкими.
- **Репозиторий на модуль с двумя реализациями: mock и http.** Демо-данные отделены от реального API; переход на backend не требует менять виджеты. Несогласованные методы выбрасывают `contract_pending`, ничего не выдумывая.
- **Zod для ответов API и переменных окружения.** Ответ backend — внешние данные, их нужно проверять. Типы выводятся из схем, без дублирования.
- **Без TanStack Query на этом этапе.** Главная читает данные в Server Components. Подключим, когда появятся клиентские списки с фильтрами и изменения данных.
- ~~Recharts через shadcn chart~~ — удалён (28.10.2026): на главных экранах достаточно одной шкалы прогресса и простых полос; библиотеку вернём, если понадобится график, который реально помогает решению.
- **Виджеты главной — по конфигурации и через явный реестр.** Это основа настраиваемых рабочих пространств: конфигурация задаёт что и где, реестр — какой код допустим.
- **Каждый виджет — свой Suspense и своя граница ошибок (`catchError`).** Медленный или упавший виджет не ломает страницу.
- **Права в интерфейсе — только для отображения.** Реальные проверки на backend.
- **Демо-роль через `NEXT_PUBLIC_DEMO_ROLE`.** Позволяет посмотреть интерфейс глазами любой роли до появления авторизации.
- **Перенаправление `/` → `/my-day` в `next.config.ts`**, дальше «Мой день» перенаправляет руководителя и наблюдателя на их стартовую страницу. `redirect()` в странице мешает проверкам мгновенной навигации Next 16.
- ~~`hooks/use-mobile.ts` на `useSyncExternalStore`~~ — удалён вместе с боковым меню (28.10.2026).

## Этап «Продажи, карточка лида, задачи, встречи» (28.10.2026, технические)

- **Контракт backend (JWT Bearer, X-Tenant, snake_case, формат ошибок, limit/offset, деньги строкой) встроен в `lib/api`.** Преобразование имён полей и разбор ошибок — только в API-клиенте.
- **Хранение токенов — httpOnly-cookie сервера Next.js (решение владельца продукта, 28.10.2026; согласуется с backend-разработчиком).** Пару `{ access, refresh }` получает и хранит сервер Next.js; JavaScript страницы токены не видит. В Python backend уходят только заголовки `Authorization: Bearer` и `X-Tenant` — cookie-сессий backend нет. Отклонены: токены в браузере (refresh доступен скриптам, все экраны пришлось бы перевести на клиентскую загрузку) и cookie от backend (противоречит согласованному формату ответа).
- **Токен обновляет `proxy.ts` до рендера страницы.** В Next 16 cookie нельзя записать во время рендера серверных компонентов, а при ротации старый refresh сразу становится недействительным — обновление посреди рендера разлогинило бы пользователя. Серверные компоненты токены только читают (`refreshOnUnauthorized: false`), server actions могут обновлять сами.
- **Один обмен на один refresh-токен** (`exchangeRefreshToken`): параллельные запросы ждут общий результат, он помнится 10 секунд. Работает в пределах одного процесса Next.js — при нескольких серверах нужен ответ backend (вопрос в `API_CONTRACT.md`).
- **Роли backend переводятся в роли интерфейса в одном месте** (`backend-roles.ts`). Добавлена роль интерфейса «Наблюдатель» и права `records.edit`, `records.assign`.
- **Сделка = лид в воронке.** Карточка сделки и клиента — одна страница `/leads/[id]`; все разделы ссылаются на неё через `leadRoute()`.
- **Смена этапа: перетаскивание на компьютере + меню карточки «Сменить этап».** Меню работает с клавиатуры и на сенсорных экранах, где перетаскивание конфликтует с прокруткой. Без новой библиотеки (нативный HTML Drag and Drop).
- **Закрытые этапы (успех / отказ) не показываются колонками доски.** Закрытие — через диалог с обязательной причиной отказа; закрытые сделки видны в таблице с фильтром по этапу.
- **Задачи без группы не выдумываются.** Группы сроков и просрочка приходят от backend; созданные или изменённые в демо задачи собраны в группу «Изменено в демо-режиме».
- **Формы на нативных полях + Zod, без React Hook Form.** Формы пока короткие (до 6 полей); RHF подключим вместе с первой большой формой (настраиваемые поля лида).
- **Подробности задачи — в выезжающей панели, итог встречи и новые записи — в диалогах.** Список остаётся на месте, контекст не теряется.
- **Вкладки карточки лида загружаются независимо** (свой Suspense): медленная история не задерживает карточку.
- **Основное меню на экранах 1024–1279 px — только иконки** (с подписью для экранного диктора и всплывающей подсказкой): иначе пункты налезали друг на друга.

## Редизайн и новые разделы (28.10.2026, технические)

- **Мягкий графитовый фон и три слоя поверхностей** вместо почти чёрного фона: меньше утомляет при долгой работе. Акцент приглушён и занимает малую площадь.
- **Размер `text-meta` (13 px) для вторичного текста строк.** Подписи 12 px оставлены только для меток и заголовков групп. `cn` настроен знать этот токен, иначе он терялся рядом с цветом текста.
- **Одна панель на список** (`ListPanel` + `ListGroup`) вместо карточки на каждую группу; **одна строка инструментов** (`Toolbar`) вместо отдельных полос вкладок и фильтров.
- **Карточка сделки — три строки**, вся кликабельна; «на этапе с» убрано с доски (есть в таблице и карточке лида).
- **Карточка лида**: «Следующий шаг» и «Что по сделке?» объединены; справочные данные — одной колонкой без вложенных карточек; на телефоне контакты идут сразу после текущего шага.
- **Понятные ошибки по видам** (`ApiErrorState`) — особенно «раздел ещё не подключён к серверу» в режиме api.
- **«Список» использует таблицу и репозиторий «Продаж»** — один компонент таблицы, сортировка и пагинация в адресе.
- **Клиент отделён от сделки** (`features/clients`): клиент — кто это и вся история, сделка — что продаём сейчас. В демо клиенты собраны из сделок по имени; в реальном режиме — отдельная сущность backend.
- **Звонки — отдельный модуль**, вкладка «Звонки» карточки лида использует его же (прежняя схема звонков в модуле лидов удалена). Факты звонка и разбор ИИ показаны отдельно.
- **Панели по адресу** (`UrlSheet`, `?client=`, `?call=`): ссылкой на клиента или звонок можно поделиться.
- **Уведомлений-тостов пока нет**: результат действия показывается на месте (строка «демо · не сохранено», плашка с «Отменить»). Тосты добавим вместе с реальными сохранениями (Base UI Toast, без новой библиотеки).

## Вход и аккаунты сотрудников (29.10.2026)

- **Без публичной регистрации и без выбора роли на входе.** Аккаунты создают уполномоченные пользователи по иерархии: администратор платформы → директор, директор → РОП, РОП → менеджер. Роль назначает сервер.
- **Переключатель демо-роли удалён.** В демо-режиме — настоящий вход по тестовым аккаунтам; подсказка с ними видна только в демо.
- **Временный пароль генерирует сервер и показывает один раз**; копирование — готовый текст с логином, паролем, адресом входа и инструкцией. Нигде не сохраняется и не логируется.
- **Обязательная смена временного пароля** блокирует рабочие разделы на сервере, а не скрытием в интерфейсе.
- **Администратор платформы не управляет продажами:** у роли только право `platform.manage`, в шапке — только «Платформа».
- **Директор — роль `owner`**, а не `admin`. Как определять администратора платформы — блокирующий вопрос к backend (флаг в `/me/`). Смысл backend-роли `admin` (администратор компании) по-прежнему нужно подтвердить; пока она получает интерфейс директора.
- **Рабочее пространство директора — «Компания»:** отделы, их руководители и численность, создание РОПов. Аналитика директора — следующий этап.
- **Новые сотрудники без истории видят «данных пока нет»**, а не демо-цифры другого менеджера.

## Два рабочих пространства (28.10.2026)

- **Менеджер и руководитель работают в разных пространствах.** «Мой день» — что сделать сегодня по своим сделкам; «Кабинет РОПа» — управление отделом по ТЗ «Кабинет РОПа». Прежняя главная руководителя (KPI-карточки, графики, воронка, рейтинг) удалена.
- **«Мой день» — рабочее пространство, а не отчёт:** одна строка результата (оборот к ориентиру с одной шкалой, осталось, нужно в день, продажи и заработок) → «Что сделать сегодня» по срочности (сейчас / сегодня / не забыть) с расписанием рядом → 5 сделок в фокусе. Убраны: заработок отдельной карточкой, график по дням, воронка месяца, направления, «Сейчас»-плашки (их смысл вошёл в список дел).
- **Кабинет: доступ РОП, директор, админ** (право `cabinet.view`, ТЗ п. 4.1). **Наблюдатель (`viewer`) в кабинет не входит** — в ТЗ его нет; его стартовая страница — «Продажи». Подтвердить у владельца продукта.
- **Кабинет только читает данные.** «Срез на планёрку» показан выключенным: нужен Telegram и снимки на backend. Задание планов — после согласования API.
- **Числа кабинета — от backend, рядом с ними определения** (книга метрик, иконка «?»). Светофор, оценка дня, «на что сделать упор» — правила-предложения ТЗ; в демо их считает mock-слой, в реальном режиме — backend.
- **Вкладки кабинета в адресе** (`?tab=plan|quality|funnel`): грузятся данные только открытой вкладки.
- **Воронка — один способ показа:** строка на этап с полосой количества, суммой, медианой дней, числом «зависших» и пометкой «скопление». Конверсию без истории переходов не показываем (прочерк и пояснение).
- **Демо-слой применяет область видимости** (`mocks/scope.ts`), поэтому проверка «менеджер не получает чужих данных» выполняется и в демо: в ответах сервера менеджеру нет имён и записей коллег.

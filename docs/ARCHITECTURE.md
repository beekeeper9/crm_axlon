# Архитектура frontend

Стек: Next.js 16 (App Router, Cache Components, Turbopack), React 19, TypeScript strict, Tailwind CSS 4, shadcn/ui (стиль base-nova на Base UI), Lucide, Zod. Графики — простые CSS-шкалы; Recharts удалён вместе со старыми виджетами.
Backend — отдельный Python-сервис. Next.js не содержит API-маршрутов и бизнес-логики backend.

## Навигация

По ТЗ используется верхняя панель, а не боковое меню:
- основные разделы менеджера: Фокус, Продажи, После встречи, Встречи, Задачи;
- меню «Все разделы» — полный каталог по группам: Рабочее, Продажи, Поиск, Материалы, Настройки;
- отдельная кнопка «ИИ-помощник»;
- логотип ведёт на стартовую страницу роли (`homeRouteFor`): менеджер — «Мой день», РОП, директор, админ — «Кабинет РОПа», наблюдатель — «Продажи»;
- набор основных разделов зависит от роли (`primaryNavigationFor`): менеджеру — Мой день, Фокус, Продажи, После встречи, Встречи, Задачи; руководителю — Кабинет РОПа, Продажи, Встречи, Задачи, Звонки;
- справа метка «Демо-данные» и меню профиля.

Уже 1024 px основные разделы прячутся, и весь каталог открывается в выезжающей панели. Пункты скрываются по правам роли (`visibleFor`), но это только отображение.

## Правила зависимостей

- Направление импортов: `app → features → components / config / lib`. Обратных импортов нет.
- Модуль импортирует другой модуль только через его `index.ts`. Исключение — `dashboard`: это модуль-агрегатор «Моего дня», и он берёт виджеты из публичного API других модулей.
- В `components/ui` нет бизнес-логики.
- `mocks/` импортируют только mock-реализации репозиториев. «Сейчас» демо-режима — настройка `config/demo-clock.ts`; подписи «сегодня / данные на» берут его через `lib/clock.ts`.
- Модули не зависят друг от друга по кругу: карточка лида использует «Задачи» и «Встречи», а список клиентов для формы встречи передаёт страница `meetings/page.tsx`.
- Переменные окружения читаются только в `config/env.ts`.

## Данные и backend

Каждый модуль описывает репозиторий — тип с методами. У него две реализации:
- **mock** берёт данные из `mocks/`, проверяет их теми же Zod-схемами и добавляет задержку;
- **http** вызывает `apiRequest()`. Пока контракт не согласован, метод выбрасывает `ApiError("contract_pending")`.

Реализацию выбирает `NEXT_PUBLIC_DATA_SOURCE` (`mock` или `api`). Бизнес-расчёты, которые принадлежат компании (план к сегодня с учётом рабочих дней, прогноз, заработок, отбор лидов в «Фокус», рекомендации ИИ), frontend не изобретает: он показывает значения из ответа.

## Изменения данных

Ни одна операция изменения ещё не согласована с backend. Поэтому `editModeFor(role)` даёт один из трёх режимов:
- `demo` (данные mock) — изменение живёт только в состоянии браузера, подписано «демо · не сохранено» и пропадает после обновления; есть «Отменить»;
- `unavailable` (данные api) — кнопки выключены с подсказкой «Станет доступно после согласования API»;
- `read-only` — у роли нет права `records.edit` (например, наблюдатель), кнопок нет.

Когда контракт появится, демо-изменение заменяется вызовом репозитория (server action → `apiRequest`) без переписывания экранов. Оптимистичных обновлений без отката не будет.

## Ошибки загрузки

Экраны загружают данные через `tryLoad()` (`lib/api/load.ts`) и при `ApiError` показывают `ApiErrorState` по виду ошибки: «не подключено к серверу», «нет доступа», «нет связи» и т. д. — вместо общей ошибки страницы. Прочие ошибки (и `redirect`, `notFound`) идут в границы ошибок Next как раньше.

## Фильтры и списки

Фильтры, вкладки и страница хранятся в адресе (`?pipeline=&view=&q=&manager=&page=`). Серверный компонент читает параметры и запрашивает данные; клиентские `SearchInput` и `FilterSelect` меняют адрес (`router.replace` в `startTransition`), пока сервер отвечает, на экране остаётся прежний список. Ссылкой на отфильтрованный список можно поделиться.

## Вход, роли и аккаунты

- Неавторизованный пользователь — на `/login` (`proxy.ts`). Публичной регистрации нет; роль на входе не выбирается.
- После входа роль определяет система: `homeRouteFor` — администратор платформы → `/platform`, директор → `/company`, РОП → `/team`, менеджер → `/my-day`, наблюдатель → `/sales`. Запрещённые страницы проверяют право на сервере и перенаправляют на стартовую.
- Вход по временному паролю: `getCurrentUser()` пускает только на `/change-password`, пока пароль не сменён.
- `getSessionState()` — сессия без перенаправлений (страница входа и смены пароля), `getCurrentUser()` — для рабочих разделов.
- Создание аккаунтов — `features/staff`: серверное действие проверяет право, роль нового аккаунта назначает сервер (в демо — `mocks/demo-accounts.ts`, иерархия `CREATABLE_ROLE`). Временный пароль приходит только в ответе действия и не сохраняется в браузере.
- **Демо-режим:** тестовые аккаунты (`mocks/demo-accounts.seed.ts`), пароли — хеши scrypt, сессия — случайный токен в httpOnly-cookie `crm_demo_session`, хранилище в памяти сервера (сбрасывается при перезапуске). Только при `NEXT_PUBLIC_DATA_SOURCE=mock`.

## Вход и токены (режим api)

```
Браузер ──cookie (httpOnly)──▶ Next.js: proxy.ts ─▶ страница / server action ──Bearer + X-Tenant──▶ Python API
```

- `/login` — форма; server action `login` получает пару токенов (`POST /auth/token/`), кладёт её в httpOnly-cookie, читает `/me/`. Одна компания — сразу в приложение, несколько — `/select-company`.
- `proxy.ts` на каждый запрос страницы: нет refresh-токена → `/login?next=…`; access истекает (меньше минуты) → обмен с ротацией и запись новой пары в ответ и в текущий запрос; компания не выбрана → `/select-company`. В режиме mock proxy ничего не делает.
- `lib/auth/token-store.ts`: `getRenderAuth()` (только чтение — для серверных компонентов) и `getActionAuth()` (с обновлением — для server actions). Бизнес-репозитории в режиме api будут брать авторизацию отсюда.
- Выбранная компания — cookie `crm_tenant`; её проверяют по списку членств из `/me/`, а не верят на слово.
- Выход — server action `signOut`: `POST /auth/logout/` и удаление cookie в любом случае.
- Это не второй backend: Next.js не проверяет пароли и права, а только хранит токены пользователя и передаёт их Python API.

## Текущий пользователь и демо-роль

`getCurrentUser()` (один раз на запрос, `React.cache`):
- в режиме `api` — `GET /api/v1/me/` и роль в выбранной компании через `uiRoleFromBackend`; при 401 — на вход;
- в режиме `mock` возвращает демо-пользователя. Роль берётся из cookie `demo_role`, а если её нет — из `NEXT_PUBLIC_DEMO_ROLE`.

Cookie выставляет server action `setDemoRole` из меню профиля. Это не авторизация и не backend: меняется только то, каким демо-пользователем показан интерфейс. В режиме `api` action ничего не делает.

## Рендеринг и состояния

- Server Components по умолчанию. Клиентские компоненты: навигация (активный пункт), всплывающие меню, графики, границы ошибок.
- Cache Components: всё, что зависит от запроса (cookies, параметры адреса), читается внутри `<Suspense>`. Страница показывает статичную часть сразу, остальное догружается: шапка — в `(crm)/layout.tsx`, содержимое — внутри страниц.
- Каждый виджет «Моего дня» обёрнут в `WidgetErrorBoundary` (`catchError`) и `<Suspense>`.

## Рабочие пространства и доступ

Два разных пространства, а не одна страница с разными виджетами:
- **«Мой день»** (право `my_day.view`, менеджер по продажам) — только собственные данные; репозиторий не принимает «чей», backend берёт сотрудника из токена.
- **«Кабинет РОПа»** (право `cabinet.view`: РОП, директор, админ) — данные отдела. Страницы `/team` и `/team/[id]` проверяют право на сервере и перенаправляют остальных на их стартовую страницу; данные кабинета backend обязан отдавать только этим ролям.

Область видимости в демо-режиме (`mocks/scope.ts`) повторяет правило backend own/team/all: менеджер получает только свои сделки, задачи, встречи, звонки, клиентов и «Фокус», даже если страница запросила чужие; чужой лид или звонок — как 404. Скрытие на frontend не используется как защита.

Настраиваемая раскладка виджетов (прежний `features/workspace` + `DashboardGrid`) удалена вместе со старой главной: сейчас у каждого пространства продуманная фиксированная композиция. Настройка вернётся на уровне секций, когда будет утверждён сценарий настройки РОПом (см. `DECISIONS.md`).
